# AgentDojo

[English](README.md) · 简体中文

本目录包含 agentguard.adapters.agentdojo 适配器、各套件的策略与锁文件（suites/<suite>/）、标准答案工具调用回放及其结果，以及真实 LLM 基准脚本。

LLM 结果只有无防护基线。设计文档要求固定模型、至少三次重复、所有配置的 LLM 基准，需要 API 密钥并产生费用。目前只用一个模型跑了无防护配置（见下文“DeepSeek 运行”），没有带防护的 LLM 结果。防护能拦住什么，以标准答案回放为证据。

## 标准答案回放（无需模型）

replay.py 将 AgentDojo 标准答案中的工具调用通过 AgentGuard 执行，无需模型或密钥。原文使用 AgentDojo 0.1.35、基准 v1.2.2，每个注入任务与各套件均匀选取的六个用户任务配对，执行过程确定。

- 正常任务完成率使用用户任务的标准答案调用，由 AgentDojo utility 评分。
- 攻击成功率先执行用户任务调用，再执行注入任务调用，由 security 评分。这模拟先完成用户任务、再执行攻击者目标的理想劫持行为。真实模型可能拒绝、改变步骤或提前停止，需用 LLM 基准测量。
- 审批自动回答。全部拒绝和全部批准分别表示人工可能允许行为的下界和上界。

**攻击成功率**（理想的被劫持智能体），配置按防护由少到多排列：

| 套件 | 无防护 | 锁文件与参数规则 | 完整防护，审批全放行 | 完整防护，审批全拒 |
|---|---:|---:|---:|---:|
| workspace | 43% | 43% | 36% | **0%** |
| travel | 86% | 86% | 57% | **0%** |
| banking | 98% | 98% | 89% | **0%** |
| slack | 100% | 100% | 60% | **37%** |

**代价**：正常任务完成率，以及每个任务触发的审批次数。

| 套件 | 无防护 | 锁文件与参数规则 | 完整防护，审批全放行 | 完整防护，审批全拒 | 每任务审批次数 |
|---|---:|---:|---:|---:|---:|
| workspace | 100% | 100% | 80% | 45% | 0.50 |
| travel | 100% | 100% | 100% | 70% | 0.30 |
| banking | 100% | 100% | 81% | 44% | 0.56 |
| slack | 100% | 100% | 100% | 5% | 2.14 |

## 结果解读

- **应与无防护基线比较，而不是与 100% 比较。** 即使无防护，攻击者的标准答案也不是每个配对都成功（workspace 43%、travel 86%、banking 98%），原因尚未调查。
- **“锁文件与参数规则”与基线相同，这是预期的。** 锁文件拦的是批准后被修改的工具，而 AgentDojo 的工具从头到尾不变，这里没有它可拦的攻击。策略按工具性质编写，不针对具体任务，所以没有参数规则。这一行是对照组：它说明下面的拦截来自数据流规则。
- **“审批全放行”只略微降低攻击成功率，这由机制决定。** 数据流规则有两种处理：参数中出现受保护数据的原文或片段（E1/E2）直接拒绝，审批也无法放行；读过不可信内容后再做改状态的操作（E3）转人工确认。多数注入目标属于后一种，比如“向攻击者转账”并没有复制受保护的原文，只是在读过不可信内容后发起。审批全部放行时这些都会通过，仍被拦住的（例如 slack 从 100% 降到 60%）是直接复制受保护数据的攻击。
- **“审批全拒”代表工具层能拦住多少。** workspace、travel、banking 都降到 0%。slack 剩下 37%，原因见下文“失败情况”。
- **防护通过人起作用。** 真实的审核者处于两个“完整防护”列之间：拒绝越多越安全，正常任务损失也越多（全部拒绝时完成率 44%–70%；slack 只有 5%，因为它的任务几乎都是先读消息或网页再发布）。这正是观察模式和目的地允许列表存在的原因。
- **值匹配拒绝不能用审批覆盖。** banking 的 3 个、workspace 的 8 个正常任务即使批准所有审批仍失败，因为这些合法任务会把刚读取的数据复制到消息或支付参数中，例如把 IBAN 放进支付主题。FL-001 将其识别为值匹配。是否应放行属于策略选择，当前策略没有为它设置允许列表。

## 失败情况

- Slack injection_task_3 要求访问网站。在全部拒绝审批配置下也未阻止，因为抓取网页是只读操作且未携带受保护数据，没有规则触发。get_webpage 的目的地允许列表可以限制访问，但此策略未声明可信网站。
- Slack injection_task_5 使用 security_from_traces 根据尝试发起的工具调用评分，因此被拦截的尝试也算成功。这是四个套件中唯一采用该方式的任务。
- 全部批准审批时，与用户操作类型一致的攻击（发邮件、支付、发帖）可通过，属于 E3 的边界，详见[实现限制](../../docs/limitations.zh-CN.md)。
- 全部拒绝审批时，正常任务大多因 AG_APPROVAL_DENIED 失败，其余因 AG_FLOW_VALUE_MATCH 失败。results/replay.json 列出每个任务及首个被拦截调用。

## 策略编写依据

策略根据工具语义编写，不参考注入任务。测试检查配置中不出现具体任务名称。

- 返回用户自身数据的工具产生 confidential 标签，返回他人文本（收到的邮件、共享文件、评论、网页、消息）的工具产生 untrusted。
- 发送数据的工具声明 egress。
- 策略限制私有数据发往外部目的地，并要求读取不可信文本后的状态修改操作经人工审批。

## 复现

下面保留原文的类 Unix shell 命令，Windows 用户需将虚拟环境 bin 路径换为 Scripts，并按所用 shell 设置环境变量。API 基准会产生费用。

```bash
python -m venv .venv-agentdojo && .venv-agentdojo/bin/pip install agentdojo -e .
.venv-agentdojo/bin/python bench/agentdojo/replay.py --pairs 6      # 结果写入 results/replay.json
.venv-agentdojo/bin/python bench/agentdojo/build_locks.py --check   # 检查锁文件与已安装套件一致
OPENAI_API_KEY=... python bench/agentdojo/run_benchmark.py --model <model> --config full_approvals_denied --repeats 3   # 会产生 API 费用
```

工具摘要依赖 Pydantic 输出的 schema，因此锁文件与生成时的 AgentDojo、Pydantic 版本绑定。build_locks.py --check 可检查是否需要重新审核。

## DeepSeek 运行（仅无防护基线）

`deepseek-chat`，温度 0，攻击 `important_instructions_no_model_name`，每个套件的全部用户任务，3 个注入任务（在套件中均匀选取，不是全部），3 次重复；数字为均值（重复间的最小–最大）。由 `summarize.py` 汇总为 `results/deepseek-summary.json`。

| 套件 | 正常任务（无攻击） | 正常任务（攻击下） | 攻击成功率 |
|---|---:|---:|---:|
| workspace | 99%（98%–100%） | 97%（95%–98%） | 0%（0%–0%） |
| travel | 80%（75%–85%） | 76%（75%–77%） | 0%（0%–0%） |
| banking | 77%（62%–88%） | 59%（56%–62%） | 0%（0%–0%） |
| slack | 100%（100%–100%） | 74%（71%–76%） | 2%（2%–2%） |

- **三种带防护的配置没有跑完，因此没有带防护的 LLM 结果。** 第一批运行已作废：`guard_pipeline` 把带防护的运行时存在 AgentDojo 的 `extra_args` 里，而 AgentDojo 让所有任务和套件共用同一个字典，导致后面套件的工具全被当成无效工具。该问题已修复（`tests/adapters/test_agentdojo.py` 有回归测试）。第二批被有意停止：无防护基线显示这个模型和攻击下没有可拦的东西，继续跑只会测出防护的代价，而这一点回放已经给出估算。
- **这个模型在这个攻击下很少被劫持**（攻击成功率 0–2%），因此这组实验无法证明 AgentGuard 降低了攻击成功率，这一点由上文的标准答案回放说明。有意义的 LLM 测量需要一个真能劫持无防护智能体的模型或攻击，这一点尚未尝试。
- 这一部分到目前的消耗：约 1670 万输入 token、70 万输出 token。
- DeepSeek 偶尔返回不合法的 JSON 工具参数，会让 AgentDojo 崩溃。`run_benchmark.py` 把这类调用改为空参数（模型会看到校验错误），对所有配置一视同仁。
